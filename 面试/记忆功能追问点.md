# 记忆功能面试追问点

> 对应简历"记忆层"描述。每个追问点都附了真实实现位置，答案必须能落到代码上。

## 1. Checkpointer 是怎么接进图的？

**两层接线：编译期 + 运行期。**

- **编译期**：`server/src/graphs/customer-graph.ts` 里 `graph.compile({ checkpointer, store })`。checkpointer 是可选参数，编译时注入，图本身不知道存储细节（依赖倒置）。
- **运行期**：每次请求 `graph.stream(input, { configurable: { thread_id, user_id } })`（`graph.service.ts`）。LangGraph 执行完**每个节点**都会把全量 State 序列化写进 checkpoint 表；下次同 thread_id 进来，先恢复上次的状态再接着跑。
- **存储层**：`PostgresSaver` 在 Nest 里通过异步 Provider 装配（`graph.module.ts`），`new PostgresSaver(pool)` **复用已有的 pg 连接池**（和 PGVectorStore 共享），启动时 `await saver.setup()` 幂等建表（checkpoints / checkpoint_blobs / checkpoint_writes）。

追问预备：为什么不用自带的 `MemorySaver`？——它是纯内存版，重启即丢，只能用于开发调试；生产要跨重启/多实例就必须落库。

## 2. thread_id 和 user_id 分别对应哪层记忆？为什么是两个维度？

| 标识 | 作用域 | 对应记忆 | 隔离方式 |
|---|---|---|---|
| `thread_id` | 一次会话 | 短期记忆（Checkpointer） | 每个会话独立一份状态 |
| `user_id` | 跨会话 | 长期记忆（Store） | 命名空间 `['memories', userId]` |

**为什么分开**：用户偏好（称呼、喜欢的颜色）属于用户这个人，换会话也该记得；而对话上下文属于具体某次会话，点"清空"就该归零。前端实现（`useGraph.ts`）：清空时只重新生成 threadId，userId 持久化在 localStorage 不变。

类比：thread_id 是"聊天记录"，user_id 是"客户档案"。

## 3. 摘要压缩为什么放在 answerSynthesizer 之后，而不是图的开始？

三个理由：

1. **当前轮不能被压缩**：本轮的 userInput 和刚生成的回答是最新鲜的上下文，必须完整保留。放在轮末压缩，`slice(0, -KEEP_RECENT)`（保留最近 4 条）语义清晰；放轮首的话刚加进来的消息也要特殊处理。
2. **触发时机精确**：answerSynthesizer 执行完，本轮融资的消息数是确定的，`shouldSummarize` 用 `messages.length > 10` 判断即可；轮首判断则要考虑"这轮还会加几条"。
3. **这是 LangGraph 官方教程的标准模式**（summarization 在对话链路末端），面试官容易对齐认知。

实现要点（`summarize.ts`）：
- 摘要是**增量合并**的——旧摘要 + 新删的消息一起喂给 LLM，生成新摘要，信息不丢
- 删除旧消息用 `RemoveMessage({ id })`，只能删 checkpoint 里带 id 的历史消息，不能碰当前轮新消息

## 4. withStructuredOutput 在 DeepSeek 上踩的坑（response_format 400）

**现象**：memoryWriter 节点静默失败，日志 `[memoryWriter] 400 This response_format type is unavailable now`，store 表始终为空，但主对话流程正常（因为节点里 try/catch 兜底了）。

**原因**：LangChain 的 `withStructuredOutput(schema)` 默认走 OpenAI 的 `json_schema` response_format；DeepSeek 不支持该格式（只支持 `json_object` 和 function calling）。

**修复**：显式指定走工具调用方式：

```ts
createModel({ temperature: 0 }).withStructuredOutput(memorySchema, {
  method: 'functionCalling',
});
```

DeepSeek 的 function calling 是可用的（项目里 React Agent 的工具调用一直正常），所以换到这个通道就通过了。

**面试讲法**：这是"用兼容层（OpenAI 协议接 DeepSeek）时的典型隐性差异——接口兼容不等于参数兼容"，踩到之后先看日志定位（400 + response_format 关键字），再查 LangChain 是否提供降级参数。

## 5. 补充追问预备（高频延伸）

- **为什么不直接把全量历史塞 prompt？** —— Token 成本线性增长 + 模型长上下文注意力稀释。摘要压缩后上下文长度恒定（4 条消息 + 一段摘要）。
- **为什么长期记忆用 Store 而不是也用 checkpointer？** —— checkpointer 的 key 是 thread_id，跨会话查不到；Store 是按命名空间的 KV 存储，天然适合"按用户维度"存取，且支持语义检索（store_vectors）。
- **memoryWriter 怎么防止记忆越写越多？** —— LLM 每轮重新生成**完整记忆列表**（上限 10 条），diff 写回：新增 put、消失 delete；key 是内容前缀的确定性哈希，重复事实 upsert 而非重复插入。
- **前端不传 history 了，刷新页面怎么办？** —— 刷新丢的只是前端渲染，服务端 checkpoint 还在（`GET /api/graph/history?threadId=` 可取回），前端可据此恢复 UI。

## 16. 长期记忆是什么时候写入和读取的？是异步还是同步写入的？如何异步写？为什么要异步写入？

### 写入时机
- **原来是同步的**：`memoryWriterNode` 是工作流的最后一个节点，图执行到它才写，用户要等它执行完才能收到最终回答
- **现在是异步的**：长期记忆写入已从工作流节点中移出，改为图执行完成后的**后台 fire-and-forget 副作用**（见 `graph.service.ts` 的 `stream` 方法）

### 读取时机
- **同步读取**：`recallMemoriesNode` 是工作流的第一个节点，每次对话开始时同步从 Store 召回用户记忆，写入 `state.userMemories` 供后续节点使用
- 必须同步，因为后面的意图路由、订单查询、RAG 检索、答案生成都可能用到用户偏好

### 如何异步写
在 `GraphService.stream()` 中：
1. 用 `async *` 异步生成器透传所有流式输出
2. 收集到 `finalAnswer` 后，等流式输出全部完成
3. 通过 `graph.getState(config)` 读最新的 checkpoint 状态（拿到完整 messages 和 summary）
4. 组装 state 后调用 `memoryWriterNode(state, config)`，用 `.catch()` 捕获错误并打日志
5. 整个过程用 `.then().catch()` 链式调用，不 `await`，不阻塞生成器返回

### 为什么要异步写入
1. **用户体验**：长期记忆写入需要调一次 LLM（提取记忆）+ 多次数据库操作（diff 写回），延迟几百毫秒到几秒不等。用户不需要等这个，答案出来就应该立刻结束对话
2. **不影响主流程**：记忆写入是锦上添花的功能，即使失败了也不影响对话正常进行
3. **符合记忆的特性**：记忆是"事后总结"，不是实时必要的，晚个几秒写入完全没问题

### 为什么读取不能异步
- 记忆召回是后续节点的输入，必须在意图路由和答案生成之前完成
- 否则 LLM 不知道用户偏好，回答质量会受影响

## 17. 长期记忆是什么时候读取的？是异步还是同步读取的？

### 读取时机
- 工作流第一个节点 `recallMemoriesNode`，每次对话开始时读取
- 在 `intentRouter`（意图路由）之前，确保后续所有节点都能拿到用户记忆

### 同步读取
- `recallMemoriesNode` 是图中的同步节点，`await store.search(...)` 等待读取完成
- 读取结果写入 `state.userMemories`，供后续节点通过 `buildMemoryContext()` 注入 prompt

### 容错设计
- 如果 store 不可用或 userId 为空，返回 `{ userMemories: [] }`，不阻断对话
- catch 住异常，只打日志，对话继续进行

### 读取到的记忆怎么用
通过 `buildMemoryContext(state)` 拼接成上下文文本，注入到：
- `orderAgentNode`：辅助理解"我的订单"这类指代
- `generalChatNode`：让回复更个性化（比如知道用户的称呼、偏好）
- `answerSynthesizerNode`：最终答案合成时参考用户偏好
- `ragNode`：问题改写时结合用户偏好，改写更准确

## 18. 长期记忆的 key 是如何生成的？

### 当前方案
```ts
const memoryKey = (text: string) => `m_${text.slice(0, 60)}`;
```
用记忆文本的前 60 个字符作为 key，加上 `m_` 前缀。

### 设计思路
- **确定性 key**：相同内容生成相同的 key，重复写入就是 upsert（更新），不会重复插入
- **简单高效**：O(1) 字符串截取，不依赖外部服务
- **可排查**：key 本身就是内容前缀，排查问题时看一眼 key 就知道大概是哪条记忆

### 适用场景
- 记忆条数上限 10 条，数量级小
- 电商客服场景记忆以事实陈述为主（"用户喜欢蓝色"、"用户穿L码"），表述相对固定
- 重复记忆即使有个两三条，对 LLM 理解影响不大

### 局限性（面试时主动提到，体现有思考）
- **语义重复问题**：语义相近但表述不同的记忆会被当成两条（如"用户喜欢蓝色"和"用户偏爱蓝色"）
- **截断风险**：60 字符以内相同但后面不同的两条记忆，会互相覆盖（概率较低，因为记忆一般都是短句）
- **没有层级/分类**：所有记忆平铺，条数多了后检索和管理都不方便

### 未来优化方向（如果条数上去了）
1. **向量相似度去重**：每条记忆做 embedding，新记忆和已有记忆算余弦相似度，超阈值就合并
2. **LLM 生成时就去重**：现在 LLM 已经是重新生成完整列表了，可以在 prompt 里更强地要求去重和合并
3. **记忆分类/层级**：按"偏好"、"历史订单"、"个人信息"等分类存储，检索更精准
4. **记忆重要性评分**：给每条记忆加重要性分，淘汰不重要的

### 为什么现在不优化
- 10 条上限下，收益小于成本
- 优先保证功能稳定和可靠性，优化排在后面
- 这是典型的"过早优化是万恶之源"的场景——先跑通验证价值，再打磨细节

## 19. 如何验证长期记忆是否写入和读取正常？

### 1. 日志验证（最直接）
代码里已经打了日志：
- 读取时：`[recallMemories] 召回 N 条长期记忆`（`recall-memories.ts`）
- 写入时：`[memoryWriter] 用户 XXX 记忆更新：M → N 条`（`memory-writer.ts`）
- 异常时：`[memoryWriter] 错误信息`（catch 里打的）

直接看服务端日志就能确认有没有读写成功。

### 2. 数据库直接查询
Store 的底层表是 `store`，可以直接查：
```sql
SELECT key, value FROM store WHERE namespace = '{"memories","用户ID"}';
```
或者查记忆表的所有数据：
```sql
SELECT * FROM store LIMIT 20;
```

### 3. 对话功能验证（端到端）
**写入验证**：
1. 开一个新会话（带 userId）
2. 说一些有记忆价值的话，比如"我叫小王，平时喜欢穿蓝色的衣服"
3. 等对话结束，看日志里有没有 `[memoryWriter]` 的输出
4. 查数据库确认记忆写入了

**读取验证**：
1. 同一个 userId 开一个新会话（新 thread_id）
2. 问"你知道我喜欢什么颜色吗"
3. 看 AI 能不能回答出"蓝色"
4. 看日志里有没有 `[recallMemories] 召回 N 条长期记忆`

### 4. history 接口辅助验证
`GET /api/graph/history?threadId=xxx` 可以查看短期记忆的状态，但看不到长期记忆。
长期记忆的验证主要靠日志和数据库。

### 5. 测试用例（如果要自动化）
可以写一个集成测试脚本：
1. 新建会话，发送"我叫测试用户"
2. 等待记忆写入（轮询日志或数据库）
3. 用同一个 userId 新建会话
4. 发送"你知道我叫什么吗"
5. 断言回答中包含"测试用户"

### 常见问题排查
- **记忆没写入**：先看 userId 传了没（没传 userId 会直接跳过），再看 LLM 调用有没有报错（DeepSeek 的 response_format 坑）
- **记忆没读取**：检查 userId 是否一致，namespace 是否正确（`['memories', userId]`）
- **记忆重复**：正常现象，当前 key 方案的已知局限，条数少不影响使用

## 20. 短期记忆如果出问题了，如何排查？

短期记忆的链路是：**前端 threadId → API 请求 → Graph/Agent Service → PostgresSaver → checkpoints + checkpoint_blobs 表**。出问题时按这条链路从外到内逐层排查。

### 排查步骤（从易到难）

#### 第一步：确认前端 threadId 有没有传
- 打开浏览器 DevTools → Network，看发送的请求 body 里有没有 `threadId` 字段
- 看 Application → Local Storage，有没有 `chat_thread_id` / `agent_thread_id` / `graph_thread_id`
- **常见坑**：清空对话后 localStorage 被清了，下一条消息是新会话（正常现象，不是 bug）
- **另一个坑**：切页面了？chat 和 agent 各用各的 threadId key，不互通（设计如此，namespace 不同）

#### 第二步：看服务端入口有没有拿到 threadId
- 在 controller 入口打日志，确认 `body.threadId` 有没有值
- 如果前端传了但后端没拿到，检查 Content-Type 是不是 `application/json`，body 是不是被中间件吞了
- 对应代码：`chat.controller.ts` / `agent.controller.ts` / `graph.controller.ts` 的 `stream` 方法第一行

#### 第三步：确认 checkpointer 注入正常
- 启动日志里有没有 `[memory] PostgresSaver 就绪（共享短期记忆）`
- 没有的话：`MemoryModule` 有没有在 `app.module.ts` 里 import（标记了 `@Global()`，不用每个模块单独 import）
- 对应代码：`memory.module.ts` + `app.module.ts`

#### 第四步：数据库里查有没有写入
直接查数据库，三层表都看：

```sql
-- 1. 看 checkpoints 表有没有这条 thread 的记录
SELECT thread_id, checkpoint_id, parent_checkpoint_id,
       checkpoint->>'v' as version,
       metadata->>'source' as source,
       metadata->>'step' as step
FROM checkpoints
WHERE thread_id = 'chat:xxxx-xxxx'  -- 注意加上 namespace 前缀
ORDER BY checkpoint_id DESC
LIMIT 10;

-- 2. 看 checkpoint_blobs 表里有没有 messages channel
SELECT channel, version, type, length(blob) as blob_size
FROM checkpoint_blobs
WHERE thread_id = 'chat:xxxx-xxxx'
  AND channel = 'messages';

-- 3. 如果有，把 blob 解码出来看内容（serde 是 JSON 的话可以直接转）
SELECT encode(blob::bytea, 'escape')::jsonb as messages_blob
FROM checkpoint_blobs
WHERE thread_id = 'chat:xxxx-xxxx'
  AND channel = 'messages'
ORDER BY version DESC
LIMIT 1;
```

**排查要点**：
- `checkpoints` 有记录但 `checkpoint_blobs` 没 `messages` channel → 消息没序列化进去，检查 state 定义
- 两张表都没记录 → checkpointer 没生效，检查 `graph.compile()` 有没有传 `checkpointer`
- 有记录但消息数不对 → 裁剪逻辑可能有 bug，看 `trimIfNeeded` / `summarize` 节点

#### 第五步：用 getState 代码验证
在 service 里加一行调试：
```ts
const state = await this.graph.getState(config);
console.log('[debug] state messages:', state.values.messages?.length);
```
确认代码层面拿到的状态和数据库一致。如果不一致，可能是 `thread_id` 的 namespace 前缀搞错了。

### 常见问题速查

| 现象 | 可能原因 | 排查点 |
|---|---|---|
| 刷新页面历史没了 | 前端 threadId 没存 / history 接口报错 | 看 localStorage + Network 里 history 请求 |
| 每次对话都是新会话（记不住上文） | threadId 没传到后端 / checkpointer 没注入 | 第三步 + 第四步 |
| 历史消息少了几条 | 裁剪逻辑触发了（超过最大轮数） | `DEFAULT_MAX_ROUNDS` 是多少，查 messages 数量 |
| agent 页面有记忆但 chat 没有 | 两个模块 namespace 不同，各自独立 | 查的时候 thread_id 前缀对不对 |
| 数据库有数据但 `getState` 拿不到 | thread_id 不匹配（缺 namespace / 拼写错） | 打日志确认两边的 thread_id 完全一致 |
| 写失败但不报错 | try/catch 吞了异常 | 看服务端日志，搜 `[Stream Error]` / `[Agent Error]` |

### 一个实用技巧：开一个干净会话从头跟
1. 前端点清空（确保 threadId 重置）
2. 发第一条消息
3. 立刻查数据库：`SELECT count(*) FROM checkpoints WHERE thread_id LIKE '%<新threadId>%'`
4. 应该有 1 条以上记录（每个节点结束一个 checkpoint）
5. 没有就是写入链路断了，按上面的步骤从外往里找

### 最容易踩的两个坑
1. **namespace 前缀**：`withNamespace('chat', threadId)` 会拼成 `'chat:xxx'`，直接拿前端的 threadId 去查肯定查不到
2. **RemoveMessage 要带 id**：裁剪消息用 `RemoveMessage({ id })`，只能删有 id 的消息；如果消息是手动塞的没 id，会删不掉，导致消息越积越多
