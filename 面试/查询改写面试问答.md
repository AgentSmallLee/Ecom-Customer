# 查询改写（Query Rewriting）面试问答

---

## 1. rag-chain.ts 里有查询改写吗？

没有。`rag-chain.ts` 里就是直接拿用户问题去做向量检索，没有经过 LLM 改写。

因为 rag-chain 定位是**单轮 RAG 接口**，用户每次传的都是完整问题，没有上下文需要补全。

---

## 2. 什么是查询改写？为什么需要？

查询改写就是在检索之前，先用 LLM 把用户的问题处理一下，再去检索。主要有三种类型：

### 类型一：指代消解 / 问题补全（最常用）
- **场景**：多轮对话
- **例子**：
  - 第一轮："蓝牙耳机多少钱"
  - 第二轮："续航呢" → 改写为 → "蓝牙耳机的续航是多久"
- **作用**：把省略、指代补全，让问题变成完整、自包含的问题，提升检索准确率

### 类型二：查询扩展 / 同义词补充
- **场景**：提升召回率
- **例子**：
  - "手机壳防摔吗" → 扩展为 → "手机壳抗摔能力怎么样？有没有防摔测试？跌落防护等级是多少？"
- **作用**：生成多个同义问法，分别检索再合并，召回更全

### 类型三：子问题拆分
- **场景**：复杂问题
- **例子**：
  - "蓝牙耳机和机械键盘各有什么特点，能退货吗"
  - 拆成："蓝牙耳机的特点"、"机械键盘的特点"、"退货政策"
- **作用**：复杂问题拆成多个简单问题分别检索，再合并结果，回答更全面

---

## 3. rag-chain.ts 加上查询改写更好吗？

**不一定，要看场景。**

| 场景 | 要不要加 | 原因 |
|---|---|---|
| 单轮接口（当前定位） | 不加更好 | 没有上下文，改写没意义；多一次 LLM 调用，增加延迟和成本；还可能引入改写错误 |
| 多轮对话场景 | 必须加 | 用户会说"它呢""多少钱"，不改写检索完全不准 |
| 想提升召回率 | 可选（查询扩展） | 收益有，但成本是 2-3 倍，要权衡 |

**结论**：rag-chain.ts 作为单轮接口，不加更好——简单、快、省成本、没有改写引入偏差的风险。

---

## 4. 如果 rag-chain.ts 里出现了指代怎么办？

### 情况一：rag-chain 就是单轮接口（当前定位）

**有指代是正常的，接口本身不处理多轮上下文。**

- 接口定位就是"给我一个完整问题，我返回答案"
- 调用方如果有对话历史，应该自己组装好完整问题再传进来，或者用工作流接口
- 单轮接口追求的是简单、快、无状态
- 类比搜索引擎：你只搜"续航多久"肯定不准，得自己把上下文说全

### 情况二：想让 rag-chain 也支持指代

那就需要加查询改写，但**光有问题还不够，得把对话历史也传进来**：

```
对话历史 + 当前问题 → LLM 改写 → 完整问题 → 检索
```

只有当前问题，没有历史上下文，LLM 也不知道"它"指的是什么。

所以要改的话，接口入参都得变：从 `{ question }` 变成 `{ question, history }`。

## 5. 我们项目里的实际做法

项目里有两套 RAG 调用路径，定位不同：

| 路径 | 位置 | 场景 | 有没有查询改写 |
|---|---|---|---|
| 独立 REST 接口 | `rag-chain.ts` + `rag.controller.ts` | 单轮问答、测试用 | 没有 |
| 工作流 RAG 节点 | `graphs/nodes/rag-node.ts` | 多轮客服对话 | 有（结合对话历史做问题补全） |

**为什么这么设计？**

- 职责分离：底层 RAG 能力做单一的事（检索+回答），上层工作流处理复杂的多轮逻辑
- 复用性：单轮接口简单通用，可以被其他地方调用
- 性能：不需要改写的场景就不浪费 LLM 调用

**rag-node 里的改写逻辑**：
- 先判断有没有对话历史
- 有历史的话，用 LLM 把当前问题改写为完整问题
- 改写失败（比如 LLM 出错）就回退到原问题，保证不会比原来更差
- 然后用改写后的问题去检索

---

## 6. 面试回答模板

> rag-chain.ts 这个独立的 RAG 链里**没有查询改写**，因为它是单轮接口，用户每次传的都是完整问题，没有上下文需要补全。加了反而多一次 LLM 调用，增加延迟和成本，还可能引入改写错误。
>
> 但在我们的 **LangGraph 工作流**里（rag-node.ts），是有查询改写的——因为工作流是多轮对话，用户可能说"它多少钱""续航呢"这种省略和指代，需要结合对话历史把问题补全再去检索，不然检索效果会很差。
>
> 查询改写主要有几种类型：
> 1. **指代消解 / 问题补全**：多轮对话里把"它""这个"补全，最常用
> 2. **查询扩展**：补充同义词、相关术语，提升召回率
> 3. **子问题拆分**：复杂问题拆成多个简单问题分别检索
>
> 我们项目主要做的是第一种，而且有降级策略——改写失败就回退到原问题，保证不会比原来更差。
>
> 我觉得设计原则就是：**单轮场景不改写，多轮场景必须改**，不要为了加功能而加功能，要看实际场景需不需要。
