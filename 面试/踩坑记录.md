# 踩坑记录（真实排查过程）

> 都是这个项目开发/联调过程中实际遇到的问题，有日志和修复代码佐证。面试讲踩坑要讲：现象 → 定位过程 → 根因 → 修复。

## 1. withStructuredOutput 调 DeepSeek 报 400

**现象**：长期记忆功能上线后，对话一切正常，但 `store` 表始终是空的（0 行）。用户偏好永远记不住。

**定位**：
1. 先怀疑写入逻辑没执行——查服务日志，发现每轮都有 `[memoryWriter] 400 This response_format type is unavailable now`
2. 报错被节点里的 try/catch 吃掉了，所以主流程无感知——这也是为什么"对话正常但记忆为空"这种静默故障比崩溃更危险

**根因**：LangChain 的 `withStructuredOutput()` 默认使用 OpenAI 的 `json_schema` response_format 让模型输出结构化 JSON；DeepSeek 的 API 不支持这种格式（只支持 `json_object`），直接拒绝请求返回 400。

**修复**（`server/src/graphs/nodes/memory-writer.ts`）：

```ts
// 显式走 function calling 方式的结构化输出
const structuredModel = createModel({ temperature: 0 }).withStructuredOutput(memorySchema, {
  method: 'functionCalling',
});
```

验证：修复后日志输出 `[memoryWriter] 用户 U-test02 记忆更新：0 → 2 条`，store 表出现"用户称呼为小牛""用户偏好蓝色"两条记忆，跨会话召回成功。

**教训**：走 OpenAI 兼容协议接第三方模型（DeepSeek/智谱/千问），**接口兼容 ≠ 参数兼容**。高级特性（json_schema、部分工具调用行为、stream_options）各家支持度不同，报错信息里带具体不支持的参数名（这里是 response_format）是关键线索。

## 2. 接 Checkpointer 前的隐藏缺陷：AI 回复从未写入 state.messages

**现象（预判型）**：接 checkpointer 之前发现，原图的 5 个节点**没有任何一个**把 AI 的回复 append 进 `messages` 状态通道——`generalChat` / `answerSynthesizer` 只返回 `{ finalAnswer }`，用户消息靠 `GraphService` 拼进初始输入。

**为什么之前没暴露**：旧架构里历史由前端回传，`messages` 只是"本次请求的临时上下文"，用完即弃，丢了 AI 消息也无所谓（`generalChat` 从前端 history 里能看到 assistant 消息）。

**为什么接 checkpointer 后就是 bug**：短期记忆完全依赖 `messages` 通道的累积。如果 AI 回复不落进去，checkpoint 里存的就是"半边对话"——只有用户在说话、没有客服回应，多轮续接时模型看到的是畸形历史。

**修复**（`server/src/graphs/nodes/answer-synthesizer.ts`）：两个分支（general 透传 + 查询合成）统一追加：

```ts
if (intent === 'general' && finalAnswer) {
  return { finalAnswer, messages: [new AIMessage(finalAnswer)] };
}
// ...
return { finalAnswer: result, messages: [new AIMessage(result)] };
```

**验证方式**：同 threadId 发两条请求，第二条问"我刚才说我叫什么名字？"——服务端没收到任何 history 却能答对，说明 checkpoint 里的对话是完整的（用户的 HumanMessage + 客服的 AIMessage 都在）。

**教训**：架构迁移会改变"旧缺陷的暴露面"。前端回传 history 时无所谓的问题，服务端接管记忆后就是致命 bug。

## 3. RemoveMessage 的类型约束：id 可能是 undefined

**现象**：`tsc --noEmit` 报隐式 any / 类型不匹配。`BaseMessage.id` 的类型是 `string | undefined`，直接 `new RemoveMessage({ id: m.id })` 过不了 strict 模式。

**根因**：LangGraph 里消息 id 是由 checkpoint 系统在持久化时分配的，内存中刚创建的消息没有 id。所以 `RemoveMessage` 只能删除"checkpoint 里带 id 的历史消息"——这其实是特性而非缺陷：天然防止误删当前轮新消息。

**修复**（`server/src/graphs/nodes/summarize.ts`）：

```ts
messages: oldMessages
  .filter((m) => m.id != null)
  .map((m) => new RemoveMessage({ id: m.id! })),
```

## 4. PostgresStore 的连接池生命周期（设计期规避）

**背景**：`@langchain/langgraph-checkpoint-postgres` 里两个类的连接池策略不同：

| 类 | 连接池 | 关闭责任 |
|---|---|---|
| `PostgresSaver` | 构造函数接受现有 `pg.Pool` | **绝不调用 `saver.end()`**——会关掉全局共享池，殃及 PGVectorStore |
| `PostgresStore` | `fromConnString()` 自建池 | 必须在应用关闭时 `store.stop()`，否则连接泄漏 |

**处理**（`graph.module.ts`）：GraphModule 实现 Nest 的 `OnApplicationShutdown`，只对 store 调 `stop()`；saver 的共享池交给进程退出统一回收。

**教训**：混用"共享连接池"和"自管连接池"的库时，先查清每个连接的生命周期归属，否则 nodemon 每次热重启都在泄漏连接。

## 5. 环境类小坑（开发过程）

- **EADDRINUSE**：自己起服务前端口 3000 已被占用（用户手动起过一个实例）——排查时先 `lsof -i :3000` 确认谁在监听，别急着 kill。
- **依赖装错目录**：用 pnpm 在仓库根目录装了 `@langchain/langgraph-checkpoint-postgres`，包落在根目录 `node_modules` 而非 `server/node_modules`。Node 的模块解析会逐级向上查找所以能跑通，但和 server 里的 `package-lock.json`（npm）形成了混管——规范做法是在 `server/` 目录内安装。
