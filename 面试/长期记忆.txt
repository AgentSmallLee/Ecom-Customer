1.长期记忆的作用是什么

  一句话：让客服系统跨会话记住用户的稳定信息，不用每次重复说。

  具体说明：
  - 短期记忆（checkpoint）只能记住当前会话的上下文，用户下次再来就全忘了
  - 长期记忆解决这个问题——跨会话保存用户的偏好、习惯、重要事实
  - 电商场景下典型的记忆内容：
    · 用户偏好（颜色、尺码、喜欢的品类）
    · 用户称呼
    · 长期诉求（比如过敏、特殊需求）
    · 历史沟通中的重要信息
  - 价值：提升用户体验，回答更个性化，用户不用重复交代

2.长期记忆是如何实现的

  核心方案：LangGraph PostgresStore + LLM 全量重估。

  存储层：
  - 存在 PostgreSQL 的 store 表里（LangGraph 框架自动创建，不是我们建的）
  - value 字段是 jsonb 类型，我们存 { text: "..." } 格式
  - 用命名空间隔离用户：['memories', userId]，每个用户的记忆互不干扰
  - key 用记忆内容的前 60 字生成（m_${text.slice(0, 60)}），
    相同内容 key 相同 → store.put 天然 upsert → 不会重复插入

  计算层（memory-writer.ts）：
  - 每轮对话结束后，把「已有记忆 + 本轮对话」一起喂给 LLM
  - 让 LLM 重新生成完整的记忆列表（prompt 要求最多 10 条）
  - 然后和旧记忆做 diff：
    · 新列表有、旧列表没有 → put 写入（新增）
    · 新列表没有、旧列表有 → delete 删除（淘汰）
    · 两边都有 → 不变

  关键设计点：
  - 不是追加写入，是每轮全量重估——LLM 自己判断哪些该留、哪些该删
  - 用内容当 key，天然去重，相同事实不会存多条
  - 纯副作用节点，try-catch 包裹，失败不影响主流程
  - temperature=0，保证输出稳定

3.长期记忆什么时候读取

  在对话开始时读取，作为 system prompt 的一部分注入给 LLM。

  具体位置：
  - LangGraph 图的第一个节点（或 recall-memories 节点）
  - 用户发来消息、开始处理这轮对话之前
  - 从 store 里查出该用户的所有记忆，拼到 system prompt 里
  - 这样 LLM 在生成回答时就知道"这个用户有哪些偏好"

  读取代码：
  - store.search(['memories', userId], { limit: MAX_MEMORIES })

4.长期记忆什么时候更新写入

  在每轮对话结束时写入，也就是最终回答生成之后。

  具体位置：
  - LangGraph 图的最后一个节点（memoryWriterNode）
  - 用户的问题已经回答完了，再回头看本轮对话有没有值得记住的

  为什么放在最后：
  - 要等回答生成完了，才能完整判断本轮有什么信息值得记
  - 先回答后记，记忆写入不阻塞用户拿到回答
  - 失败了也不影响主流程，用户无感

  处理流程：
  1. 拿到 userInput（用户输入）和 finalAnswer（最终回答）
  2. 从 store 读取已有记忆
  3. 调 LLM 生成更新后的记忆列表
  4. 和旧记忆对比，增删改写回 store

5.长期记忆会不会越存越多，如何处理的

  不会越存越多，有两道防线控制。

  第一道：数量上限（MAX_MEMORIES = 10）
  - prompt 里明确要求 LLM 最多输出 10 条
  - 从源头限制了记忆的最大数量

  第二道：全量重估机制（更关键）
  - 不是每轮追加一条，而是每轮让 LLM 重新生成完整列表
  - LLM 会主动判断：哪些还有价值保留，哪些过时了该删掉
  - 记忆数量是波动的（可能这轮 5 条，下轮 4 条，再下轮 6 条）
  - 不是只增不减，而是有增有减，动态平衡

  为什么不用 FIFO（淘汰最老的）？
  - 长期记忆里，最老的往往是最有价值的（比如"用户喜欢红色"）
  - 最新的反而是一次性的（比如"用户查了订单123"）
  - FIFO 会把最该留的删掉，留着没用的，方向反了
  - 用 LLM 按价值淘汰才是合理的

  补充：语义相似的记忆会不会重复？
  - 当前方案是按文本内容去重的，语义相同但措辞不同会存两条
  - 但因为有 10 条上限，影响不大
  - 真要优化可以用语义去重（embedding 相似度），但成本高很多，收益不大
