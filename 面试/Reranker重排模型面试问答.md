# Reranker 重排模型面试问答

---

## 1. Reranker 需要引入单独的模型吗？

是的，**Reranker 需要单独引入一个模型**，而且和 Embedding 模型不是一回事。

---

## 2. 为什么需要单独的模型？和 Embedding 有什么区别？

两者定位不同，是"召回"和"精排"的关系：

| 维度 | Embedding 模型 | Reranker 模型 |
|---|---|---|
| 作用 | 把文本变成向量，用于快速检索 | 对"问题-文档对"打分，判断相关性 |
| 架构 | Bi-Encoder（双编码器） | Cross-Encoder（交叉编码器） |
| 输入 | 单条文本 → 向量 | （问题 + 文档）→ 相关性分数 |
| 速度 | 快（预计算 + 向量索引，毫秒级） | 慢（每条都要过模型，几十毫秒） |
| 精度 | 一般（召回用，只求别漏） | 高（精排用，只求准确） |
| 调用量 | 每次检索 1 次 | 每次检索 N 次（N = 候选数） |

### 为什么不能直接用 Embedding 的相似度当最终分数？

- Embedding 是把问题和文档**分别编码**，两个向量独立生成，交互只有最后一步点积
- Reranker 是把问题和文档**一起输入**模型，模型可以做更深层的交互和推理
- 类比：Embedding 像"扫一眼标题判断相关不相关"，Reranker 像"仔细读完内容再打分"

---

## 3. Bi-Encoder vs Cross-Encoder

### Bi-Encoder（双编码器，Embedding 用的）
```
问题 → Encoder → 向量
文档 → Encoder → 向量
相似度 = 向量点积 / 余弦相似度
```
- 优点：文档向量可以预计算，检索只需要算问题的向量，速度极快
- 缺点：问题和文档的交互只有最后一步，精度受限

### Cross-Encoder（交叉编码器，Reranker 用的）
```
<[BOS_never_used_51bce0c785ca2f68081bfa7d91973934]>问题 [SEP] 文档] → Encoder → 相关性分数
```
- 优点：问题和文档在模型内部充分交互，打分更精准
- 缺点：每一对（问题+文档）都要单独过模型，无法预计算，速度慢

## 4. 常用的 Reranker 模型

| 模型 | 说明 | 适用场景 |
|---|---|---|
| **bge-reranker-v2-m3** | 智源 BGE 系列最新，多语言，中文效果好 | 中文 RAG 首选 |
| **bge-reranker-large** | BGE 经典款，效果稳定 | 中文场景 |
| **cross-encoder/ms-marco-MiniLM-L-6-v2** | 英文经典小模型 | 英文场景 |
| **Cohere Rerank** | 商用 API，按调用量付费 | 不想自己部署 |
| **阿里云/腾讯云 文本相似度 API** | 国内云厂商 | 用云服务的场景 |

### 部署方式
- **自部署**：HuggingFace 模型 + FastAPI / TorchServe 封装成 API
- **商用 API**：Cohere、云厂商，按调用量付费

## 5. Reranker 在 RAG 流程中的位置

```
用户问题
   ↓
向量召回（top-50 / top-100）   ← Embedding 模型，快，粗筛
   ↓
关键词召回（top-50）         ← BM25，快，粗筛
   ↓
去重合并 → 候选集（约 50 条）
   ↓
Reranker 精排                ← Cross-Encoder 模型，慢，精排
   ↓
最终 top-k（3-5 条）
   ↓
拼 prompt → LLM 回答
```

### 为什么不直接用 Reranker 全量打分？

- **成本太高**：假设库里有 1 万条文档，每次检索调用 Reranker 打 1 万分，延迟和成本都爆炸
- **没必要**：99% 的文档和问题明显不相关，用 Embedding 快速筛掉就行
- **行业标准做法**：召回（快但粗）+ 精排（慢但准）的两阶段架构

---

## 6. 两阶段架构的常见组合

| 方案 | 召回 | 精排 | 适用阶段 |
|---|---|---|---|
| 纯向量 | 向量 top-k | - | 知识库小（<1000 条） |
| 混合检索 | 向量 + BM25 + RRF | - | 中等规模，对准确率有要求 |
| 混合 + Reranker | 向量 + BM25 | Reranker 精排 | 大规模，对准确率要求高 |

---

## 7. 我们项目需要上 Reranker 吗？

**目前完全不需要。**

原因：
- 知识库只有几十个 chunk，全量扫一遍都很快
- 向量检索精度已经够用了
- 上 Reranker 需要额外部署模型服务，成本和复杂度都上去了
- 收益和付出不成正比

### 什么时候考虑上？

按优先级：
1. **先上混合检索**（向量 + BM25 + RRF），成本低，收益明显
2. 混合检索还不够，再考虑 **Reranker**
3. 触发条件：知识库几千条以上、评估发现检索准确率不够

## 8. 面试回答模板

> 是的，Reranker 需要单独引入一个模型，一般用的是 **Cross-Encoder** 结构，和 Embedding 用的 Bi-Encoder 不一样。
>
> Embedding 是把问题和文档分别编码成两个向量，然后算相似度，速度快但精度一般，适合做召回；Reranker 是把问题和文档拼在一起输入模型，直接输出相关性分数，精度高但速度慢，适合做精排。
>
> 架构上一般是"**粗召 + 精排**"两阶段：先用向量检索 + 关键词检索快速捞出几十条候选，再用 Reranker 对这些候选精细打分，选出最相关的 top-k。这样既保证了召回率，又保证了准确率。
>
> 为什么不直接用 Reranker 全量打分？因为太慢太贵了——假设库里一万条文档，每次检索打一万分，延迟和成本都爆炸了。所以先用 Embedding 快速筛掉 99% 不相关的，剩下的一小撮再用 Reranker 精排，性价比最高。
>
> 常用的中文 Reranker 模型比如 BGE 的 bge-reranker-v2-m3，可以自己部署，也可以用云厂商的 API。
>
> 我们项目目前知识库还很小，向量检索效果已经够用了，所以还没上 Reranker。后面知识库规模上来、发现检索精度不够的时候，会先上混合检索 + RRF，如果还不够再考虑 Reranker——一步步来，不做过度设计。
