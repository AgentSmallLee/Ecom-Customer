4.为什么用md
  我们项目用 Markdown 主要是几个原因：
   1. 结构清晰：有标题层级，切分的时候语义更完整，检索效果好
   2. 易于维护：运营同事直接改文件就行，不需要复杂的 CMS
   3. 解析成本低：纯文本，不需要引入 PDF 解析之类的重依赖

5.你们的chunkSize和chunkOverlap，top-k参数是如何定的
  这三个参数不是拍脑袋定的，是结合我们的业务场景和文档特点调出来的。

  chunkSize（目前 500 字左右）：
  - 首先看业务场景：电商客服，用户问题都比较短（几十字），问的都是具体的点（比如"能退货吗""续航多久"）
  - chunk 太大的话，一个 chunk 里包含太多信息，检索到的内容不精准，LLM 回答容易被噪音干扰
  - chunk 太小的话，一个完整的语义单元被切碎，上下文丢失，检索到的片段看不懂
  - 我们先统计了文档的平均段落长度，大概 300-600 字，所以选 500 字作为基准，保证大部分 chunk 能包含一个完整的语义单元
  - 然后实际测了几轮，发现 500 字的时候，检索到的内容和问题的匹配度最高，太大容易混进不相关内容，太小又信息不全

  chunkOverlap（目前 50 字，约 10%）：
  - overlap 的作用是防止 chunk 边界把一句话切断，保证相邻 chunk 之间有上下文衔接
  - 一般设 chunkSize 的 10%-20% 比较常见
  - 我们设 50 字，大概一两句话的长度，既能防止语义被切断，又不会导致太多重复内容
  - overlap 太大的话，冗余太多，浪费 token，也会让检索结果重复度变高
  - 太小的话，起不到衔接上下文的作用，边界处的内容检索不到

  top-k（目前 4）：
  - k 太小：信息不够，LLM 回答不充分，容易"不知道"
  - k 太大：噪音多，反而会干扰 LLM 判断，而且 token 成本高、响应慢
  - 我们选 4 是因为：
    1. 知识库不大，相关内容一般 2-4 个 chunk 就能覆盖
    2. 4 个 chunk 拼起来大概 2000 字，放进 prompt 里不会太长，模型能处理得过来
    3. 电商客服的问题大多比较具体，不需要太多上下文
  - 后来我们做了按来源去重的优化，每个来源最多 2 条，保证信息多样性，避免 4 条全来自同一个文档

  总结：
  - 参数不是一成不变的，是根据文档特点和业务场景调出来的
  - 后面如果知识库变大、问题变复杂，我们会做更系统的评估（比如用 RAG 评测集看不同参数下的召回率和准确率），再动态调整
  - 真实生产中还可以做动态 chunkSize：不同类型的文档用不同的切分参数，比如 FAQ 类的可以小一点，产品说明书类的可以大一点

6.如果从多个chunk里检索出来结果，来源有相同的，如何去重，防止前端页面显示重复
  这个是 RAG 系统非常常见的问题，chunkSize 越小越容易出现。
  关键原则：检索层和展示层要分开，检索保证质量，展示保证体验。

  第一层：展示层去重（必做，最直接）
  - 展示给用户的"引用来源"按 source 分组，同一个文件只显示一次
  - 实现方式：后端返回 sources 时按 source 去重，或者前端做分组展示
  - 进阶展示：每个来源后面标"共 N 个相关片段"，点击展开看详情
  - 注意：去重只影响展示，不影响传给 LLM 的 context
  - 我们项目现在就是这么做的：retriever 返回 4 条最相关的 chunk 给 LLM 用，
    但 sources 输出时按 source 去重，用户看到的来源不重复

  第二层：检索层多样性优化（文档多了再做）
  - 当知识库有十几个以上文档时，检索结果可能过度集中在少数文档里，
    漏掉其他文档的相关信息，这时候需要做多样性优化
  - 方案 A：MMR（最大边际相关性）重排
    · LangChain 原生支持：vectorStore.asRetriever({ searchType: "mmr", k: 4, fetchK: 20, lambda: 0.5 })
    · 在相似度基础上兼顾结果多样性，lambda 控制平衡（0=只看多样性，1=只看相似度）
    · 适合文档量中等、希望结果覆盖更多主题的场景
  - 方案 B：按来源分组采样
    · 先召回更多候选（比如 20 条），每个来源最多选 N 条，保证来源多样性
    · 适合明确知道需要覆盖多个文档的场景
  - 注意：文档量少的时候（比如只有2-3个文档），这些优化效果不明显，
    反而可能把不相关的内容硬塞进 context，降低回答质量

  第三层：Parent-Child 父子分块（大规模知识库方案）
  - 小块（child，200字左右）用来做检索，精度高
  - 大块（parent，1000字左右，一般是完整的章节或段落）用来给 LLM 当上下文
  - 检索时匹配到小块，返回对应的整块父文档
  - 优点：兼顾检索精度和上下文完整性，来源天然不重复（每个父块一个来源）
  - 缺点：实现最复杂，需要维护父子块映射关系，存储成本也更高

  我们项目的实践：
  - 目前知识库只有 2 个文档（商品+政策），文档量很小
  - 所以检索层直接用纯相似度 top-k=4，保证 LLM 拿到最相关的内容，
    不强行做多样性优化，避免引入噪音
  - 展示层做来源去重，用户看到的引用来源不重复
  - 后续如果知识库扩展到十几个文档以上，再考虑加 MMR 或其他多样性策略
  - 再往后规模大了可以上父子分块
7.RAG 中如何防止 LLM 幻觉
  1. **Prompt 约束**：明确要求 LLM "严格基于参考文档回答，不知道就说不知道"
  2. **引用溯源**：要求 LLM 引用具体文档片段，方便人工核实
  3. **温度控制**：RAG 场景通常设置 temperature=0.1\~0.3，减少随机性
  4. **检索质量**：确保检索出的上下文确实与问题相关（使用混合检索+Rerank)
