3.知识库如果需要更新，你们怎么做

  我们现在用的是**增量更新为主，全量更新兜底**的方式。

  ▎日常更新走增量：
  每个文档有唯一标识（我们用文件名当 source，存到 chunk 的 metadata 里）。
  更新时扫描知识库目录，对比每个文件的最后修改时间和数据库里的 last_ingested_at：
  - 文件是新增的 → 切分后直接写入
  - 文件被修改了 → 先按 source 删除旧的 chunk，再切分写入新的
  - 文件被删除了 → 按 source 删除所有相关 chunk
  - 文件没变 → 直接跳过
  这样每次只处理有变更的文档，秒级就完了，不用每次全量重跑。

  ▎全量更新做兜底：
  加一个 --full 参数，凌晨低峰期或者换 embedding 模型、改 chunk 大小的时候跑一次。
  全量会 TRUNCATE 后重新写入所有文档，防止增量累积的不一致。

  ▎我知道企业级还会更复杂：
  - 触发方式：除了定时同步，还会做事件驱动——文档上传/修改通过 MQ 或 Webhook 实时触发
  - 版本管理：每次全量重建生成一个新版本的索引（比如 v1、v2），通过别名切换，零停机，有问题随时回滚
  - 审核流程：运营修改的文档要审核通过才能进知识库，不能谁改了都直接上线
  - 灰度发布：新索引进了之后先只对内部用户或一小部分流量开放，验证没问题再全量切

  我们现在规模小，用简单的增量就够了，但后续可以按这个方向逐步演进。

5.你们的chunkSize和chunkOverlap，top-k参数是如何定的
  这三个参数不是拍脑袋定的，是结合我们的业务场景和文档特点调出来的。

  chunkSize（目前 500 字左右）：
  - 首先看业务场景：电商客服，用户问题都比较短（几十字），问的都是具体的点（比如"能退货吗""续航多久"）
  - chunk 太大的话，一个 chunk 里包含太多信息，检索到的内容不精准，LLM 回答容易被噪音干扰
  - chunk 太小的话，一个完整的语义单元被切碎，上下文丢失，检索到的片段看不懂
  - 我们先统计了文档的平均段落长度，大概 300-600 字，所以选 500 字作为基准，保证大部分 chunk 能包含一个完整的语义单元
  - 然后实际测了几轮，发现 500 字的时候，检索到的内容和问题的匹配度最高，太大容易混进不相关内容，太小又信息不全

  chunkOverlap（目前 50 字，约 10%）：
  - overlap 的作用是防止 chunk 边界把一句话切断，保证相邻 chunk 之间有上下文衔接
  - 一般设 chunkSize 的 10%-20% 比较常见
  - 我们设 50 字，大概一两句话的长度，既能防止语义被切断，又不会导致太多重复内容
  - overlap 太大的话，冗余太多，浪费 token，也会让检索结果重复度变高
  - 太小的话，起不到衔接上下文的作用，边界处的内容检索不到

  top-k（目前 4）：
  先做了一个 50 题左右的评测集，分别测了 top-1、top-3、top-5、top-10 的召回率，发现 top-4 的时候召回率能到 90%
  ▎ 左右，再往上边际收益很小。
  ▎
  ▎ 同时也考虑了生成质量和成本——k 太大的话上下文噪音多，token 成本也高。所以最后定了 top-4，兼顾召回率、生成质量和成本

  总结：
  - 参数不是一成不变的，是根据文档特点和业务场景调出来的
  - 后面如果知识库变大、问题变复杂，我们会做更系统的评估（比如用 RAG 评测集看不同参数下的召回率和准确率），再动态调整
  - 真实生产中还可以做动态 chunkSize：不同类型的文档用不同的切分参数，比如 FAQ 类的可以小一点，产品说明书类的可以大一点

6.如果从多个chunk里检索出来结果，来源有相同的，如何去重，防止前端页面显示重复
  这个是 RAG 系统非常常见的问题，chunkSize 越小越容易出现。
  关键原则：检索层和展示层要分开，检索保证质量，展示保证体验。

  第一层：展示层去重（必做，最直接）
  - 展示给用户的"引用来源"按 source 分组，同一个文件只显示一次
  - 实现方式：后端返回 sources 时按 source 去重，或者前端做分组展示
  - 进阶展示：每个来源后面标"共 N 个相关片段"，点击展开看详情
  - 注意：去重只影响展示，不影响传给 LLM 的 context
  - 我们项目现在就是这么做的：retriever 返回 4 条最相关的 chunk 给 LLM 用，
    但 sources 输出时按 source 去重，用户看到的来源不重复

  第二层：检索层多样性优化（文档多了再做）
  - 当知识库有十几个以上文档时，检索结果可能过度集中在少数文档里，
    漏掉其他文档的相关信息，这时候需要做多样性优化
  - 方案 A：MMR（最大边际相关性）重排
    · LangChain 原生支持：vectorStore.asRetriever({ searchType: "mmr", k: 4, fetchK: 20, lambda: 0.5 })
    · 在相似度基础上兼顾结果多样性，lambda 控制平衡（0=只看多样性，1=只看相似度）
    · 适合文档量中等、希望结果覆盖更多主题的场景
  - 方案 B：按来源分组采样
    · 先召回更多候选（比如 20 条），每个来源最多选 N 条，保证来源多样性
    · 适合明确知道需要覆盖多个文档的场景
  - 注意：文档量少的时候（比如只有2-3个文档），这些优化效果不明显，
    反而可能把不相关的内容硬塞进 context，降低回答质量

  第三层：Parent-Child 父子分块（大规模知识库方案）
  - 小块（child，200字左右）用来做检索，精度高
  - 大块（parent，1000字左右，一般是完整的章节或段落）用来给 LLM 当上下文
  - 检索时匹配到小块，返回对应的整块父文档
  - 优点：兼顾检索精度和上下文完整性，来源天然不重复（每个父块一个来源）
  - 缺点：实现最复杂，需要维护父子块映射关系，存储成本也更高

  我们项目的实践：
  - 目前知识库只有 2 个文档（商品+政策），文档量很小
  - 所以检索层直接用纯相似度 top-k=4，保证 LLM 拿到最相关的内容，
    不强行做多样性优化，避免引入噪音
  - 展示层做来源去重，用户看到的引用来源不重复
  - 后续如果知识库扩展到十几个文档以上，再考虑加 MMR 或其他多样性策略
  - 再往后规模大了可以上父子分块
7.RAG 中如何防止 LLM 幻觉
  1. **Prompt 约束**：明确要求 LLM "严格基于参考文档回答，不知道就说不知道"
  2. **引用溯源**：要求 LLM 引用具体文档片段，方便人工核实
  3. **温度控制**：RAG 场景通常设置 temperature=0.1\~0.3，减少随机性
  4. **检索质量**：确保检索出的上下文确实与问题相关（使用混合检索+Rerank)

为什么要ReRank
  因为召回阶段追求"快而全"，Rerank 阶段追求"准而精"。两者目标矛盾，必须分两阶段做。召回用 Bi-Encoder 快速从百万级文档里捞回候选，
  但精度有限；Rerank 用 Cross-Encoder 对少量候选做深度交互精算，把真正相关的排到最前，显著提升最终喂给 LLM 的上下文质量

    准确率 Precision@K Top-K 里有多少相关的
      (1) 准确率和召回率的区别
        召回率（Recall）：该回来的回来了多少？怕漏掉
        准确率（Precision）：回来的有多少是对的？怕掺假
        两个指标要平衡：K 越大召回率越高，但准确率会掉，因为混进了噪音
      (2) 怎么评估准确率
        也是用同一套评测集，不用重新标注，只要给每个问题加一个 expectedSource（正确答案在哪个文档/商品里）
        判断标准：检索结果里的 chunk 只要包含 expectedSource（比如"蓝牙耳机 X1 Pro"）就算相关
        Precision@K = top-K 中相关的 chunk 数 ÷ K
        无答案问题比较特殊：一条都没召回才算 1.0（没乱召回就是准），召回了任何东西都是 0
      (3) 我们的做法
        单独写了一个 eval-precision.ts 脚本，和召回率脚本共用评测集，支持三种模式对比
        相关标准用的是"文档标题匹配"——同一个商品/同一段政策的 chunk 就算相关
        这样不用额外标注，实现简单，也基本准确
        每次调优的时候，召回率和准确率一起看，确保不是靠牺牲准确率换召回率
  生成质量
    核心思路：LLM-as-Judge —— 用大模型当评委自动打分。
    评估维度主要有三个：

    (1) 忠实度（Faithfulness）：回答是不是严格基于上下文，有没有幻觉
        · 做法：把「回答 + 检索上下文」一起喂给 LLM，
          让它逐条核查每个信息点是否有上下文依据
        · prompt 要点：明确说明"补充相关信息不算幻觉"、
          "语气词不参与评估"，避免误判
        · 当前得分：0.975

    (2) 相关性（Relevance）：回答有没有答非所问，是不是针对用户问题
        · 做法：LLM 判断回答是否真正回应了问题
        · 当前得分：0.938

    (3) 完整性（Completeness）：该说的点有没有说到，有没有遗漏关键信息
        · 做法：基于人工标注的 answerKeywords（答案要点），
          让 LLM 做语义级别的覆盖度判断
        · 为什么不用规则匹配：中文语义匹配靠规则做不准
          （比如"商家承担"和"红松心选承担"意思一样但匹配不上），
          改成 LLM 评估后从 0.25 提到了 0.99
        · 当前得分：0.990

    我们目前的做法（结合项目实际）：
      · 48 道评测题（商品查询 37 道 + 政策查询 7 道 + 无答案 4 道）
      · 综合分 = 三个维度的平均分
      · 无答案问题特殊处理：完整性不参与评分，
        综合分只算忠实度 + 相关性（因为没有标准答案要点）
      · temperature=0，保证评分稳定
      · 当前效果：合格率 100%（综合分 ≥ 0.8），总体平均分 0.96

    评分标准与合格线：
      · 合格率 = 综合分 ≥ 0.8 的题目数 ÷ 总题目数
      · 为什么合格线是 0.8？
        1. LLM 评分本身有一定波动（同一道题两次打分可能差 0.1-0.2），留点余量
        2. 从实际体验看，0.8 分以上的回答基本准确可用，用户不会感觉到明显问题
        3. 电商客服场景允许少量瑕疵，只要不幻觉、不跑题就行
      · 效果等级参考：
        - 优秀：综合分 ≥ 0.9，合格率 ≥ 90%（可以上线，效果很好）
        - 良好：综合分 0.8~0.9，合格率 70%~90%（基本可用，有优化空间）
        - 及格：综合分 0.7~0.8，合格率 50%~70%（勉强能用，bad case 较多）
        - 较差：综合分 < 0.7，合格率 < 50%（不能上线，需要大改）
      · 三个维度的权重：忠实度是底线，绝对不能低（低于 0.7 说明有幻觉，
        其他维度再高也没用）；相关性其次；完整性相对最有弹性

    和 RAGAS 框架的关系：
      · 思路是一致的，都是 LLM-as-Judge
      · 区别：我们是轻量定制版
        - 去掉了 Context Precision / Context Recall（检索质量单独评）
        - 增加了业务关心的"完整性"维度
        - prompt 做了中文和电商场景优化
      · 为什么不直接用 RAGAS：项目早期，轻量实现更灵活，
        改 prompt、加指标都很方便；后面规模大了可以考虑引入

    踩过的坑：
      1. 上下文截断 bug：最开始评估用的上下文被截成 100 字，
         导致忠实度只有 0.78，修复后涨到 0.97
      2. 完整性评估从规则改到 LLM：关键词匹配做不准，
         政策类只有 0.25，改成 LLM 语义评估后到 0.99
      3. LLM 评分有随机性：同一道题两次打分可能差 0.5 分，
         用 temperature=0 + 优化 prompt 来稳定
      4. 评测集质量很重要：发现过一道题（保修期有多久）
         的答案要点在知识库中没有依据，删掉了这道不合理的题

    - 共同部分：question（同一个问题）
    - 检索质量标注：expectedSource / expectedKeywords，判断的是检索返回的 chunk
    - 生成质量标注：answerKeywords（答案要点关键词列表），判断的是 LLM 生成的完整回答
    - 指标不同：检索看 Recall@K / Precision@K，生成看忠实度 / 相关性 / 完整性

    为什么可以共用：
      检索和生成是一条链路，同一个问题先过检索再过生成。
      共用问题的好处：
      1. 标注成本低，不用从头建两套
      2. 方便做端到端归因——生成效果差的时候，
         可以马上看到底是检索没捞对，还是 LLM 本身有问题
         比如：某个问题生成质量差 → 查检索评估 → 发现 Recall@4=0 → 问题在检索层

    实际项目中的做法：
      在同一个 eval-set.json 里，既有检索用的字段，也有生成用的字段，比如：
      {
        "question": "蓝牙耳机多少钱",
        "category": "product",                   // 分类（检索和生成都用）
        "expectedSource": "蓝牙耳机 X1 Pro",     // 检索用：判断检索结果是否命中
        "expectedKeywords": ["899"],             // 检索用：判断召回是否准确
        "answerKeywords": ["价格 899 元", "产品名 蓝牙耳机 X1 Pro"]  // 生成用：完整性评估的答案要点
      }
      检索评估脚本读 expectedSource/expectedKeywords，
      生成评估脚本读 answerKeywords，互不干扰。

    什么时候要分开加题：
      不是所有场景都能共用，生成特有的场景需要单独加：
      1. 生成特有的 bad case：比如语气不好、格式不统一、引用格式错了
      2. 多跳/复杂推理问题：需要跨多个文档综合回答的，
         检索可能每段都命中了，但生成可能没综合好

13.评测集一般是怎么生成的，可以用 AI 生成吗
    可以用 AI 生成，而且现在工业界已经很常用了。
    但 AI 生成的是初稿，必须人工审核，不能直接拿来用。

    常见的几种生成方式：

    1. 完全人工标注（最准但最慢）
       - 从真实用户问题里挑高频/有代表性的，人工标答案
       - 优点：最准确，最贴合真实场景
       - 缺点：慢，贵，依赖人对业务的理解
       - 适用：核心评测集、上线前验收用的黄金测试集

    2. AI 生成 + 人工审核（现在最主流）
       - 流程：原始文档 → LLM 生成问答对 → 人工审核修正 → 最终评测集
       - 做法：把一段文档丢给 GPT-4，让它按不同角度出题
         （事实查询、比较类、多跳推理、无答案问题等）
       - 优点：速度快（几十分钟上百题），成本低，覆盖广
       - 缺点：需要人工审核，不然会有错题
       - 适用：大部分项目都是这个方式，性价比最高

    3. 从真实用户日志里挖掘（质量最高）
       - 从线上真实用户的提问日志里捞，人工标注答案
       - 优点：最贴近真实用户分布，评估结果最有参考价值
       - 缺点：需要有线上流量才能积累，初期没有
       - 适用：产品上线后，从人工客服记录、用户提问日志里持续补充

    4. 混合方式（最推荐的实战做法）
       核心集用人工标注（保证质量），
       长尾用 AI 生成扩充（保证覆盖），
       上线后再用真实日志持续补充。

    AI 生成需要注意的坑：
      - AI 出的题太"友好"：倾向于出文档里明确写了的简单题，不会出刁钻的
      - 答案太完美：AI 生成的答案往往直接抄文档，和真实 LLM 回答风格不一样
      - 有幻觉：可能编造文档里没有的内容当答案
      - 分布不均：简单题太多，复杂推理题、无答案问题太少

    人工审核主要看什么：
      - 问题是不是真实用户会问的？
      - 答案是不是真的能在文档里找到依据？
      - 难度分布合不合理？
      - 有没有重复或者太相似的题？

    我们项目的做法：
      先人工结合业务场景设计了一批核心问题，
      然后用 DeepSeek 读取知识库文档，批量生成补充问答对，
      再人工审核——把不真实的问题删掉，答案不对的修正，
      补充一些 AI 没想到的刁钻问题和无答案问题。
      纯人工太慢，纯 AI 又不靠谱，两者结合效率最高。

14.当前评测实现逻辑，综合得分和合格率多少认为是效果比较好的，合格率是如何算的

    ▎ 我们用综合分 0.8 作为合格线，低于 0.8 的算不合格。
   ▎
  ▎ 为什么是 0.8？一是 LLM 评分本身有一定波动，留点余量；二是从实际体验看，0.8 分以上的回答基本是准确可用的，用户不会感觉到明显问题。
  ▎
  ▎ 目前我们系统综合分在 0.9 以上，合格率接近 
  ▎ 100%，属于比较好的水平。三个维度里忠实度是重点关注的底线指标，绝对不能低——生成质量再差也不能有幻觉。

  15.面试官问，检索侧你们是如何评估的，召回率和准确率多少算合格

      检索侧我们是通过构建评测集 + 自动化脚本的方式评估的，
      核心是两个指标：召回率（Recall@K）和准确率（Precision@K）。

      怎么评估的：
      1. 先构建评测集：从高频场景里选 50 道左右有代表性的问题，
         人工标注每个问题的 expectedSource（正确答案在哪个文档/商品里）
         和 expectedKeywords（答案关键词，用来判断召回是否命中）
      2. 写自动化评测脚本：遍历评测集里的每个问题，用检索系统查 top-K，
         然后分别计算召回率和准确率
      3. 支持三种模式对比：纯向量、纯关键词、混合检索，
         同一套评测集跑三遍就能看哪个方案效果好
      4. 还会按问题类型分类统计（商品查询/政策查询/无答案），
         方便定位哪类问题效果差

      召回率（Recall@K）怎么算：
      · 判断标准：top-K 个结果里包含了正确答案（关键词匹配命中）就算召回成功
      · 公式：Recall@K = 命中的题数 ÷ 总题数
      · 是二值判断，一道题要么命中了，要么没命中，不存在中间状态

      准确率（Precision@K）怎么算：
      · 判断标准：检索结果里的 chunk，只要和 expectedSource 是
         同一个商品/同一段政策的就算相关
      · 公式：Precision@K = 所有题的相关 chunk 数之和 ÷ (题数 × K)
      · 无答案问题特殊处理：一条都没召回才算 1.0（没乱召回就是准），
        召回了任何东西都是 0

      多少算合格：
      · 召回率更重要——漏掉了正确答案，后面生成再厉害也没用
        - 优秀：Recall@4 ≥ 0.9（90% 以上的问题能召回正确答案）
        - 良好：0.8 ~ 0.9
        - 及格：0.7 ~ 0.8
      · 准确率可以稍微低一点——多捞回来一两条不相关的，
        LLM 还能自己分辨
        - 优秀：Precision@4 ≥ 0.8
        - 良好：0.7 ~ 0.8
        - 及格：0.6 ~ 0.7
      · 两个指标要一起看，不能为了召回率把 K 设得很大，
        准确率掉得一塌糊涂——要在两者之间找平衡点

      我们目前的情况：
      · 混合检索的效果最好，Recall@4 在 0.9 以上，Precision@4 在 0.8 左右
      · 纯向量检索准确率高但召回率偏低，纯关键词召回率高但准确率差
      · 混合检索（RRF 融合）兼顾了两者，是目前线上用的方案
