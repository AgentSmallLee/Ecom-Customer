# 面试：JWT 认证与 Token 流转全链路

## 一句话结论

- **JWT 是 token 的一种格式**，"从请求头传 token"是传输方式，两者不冲突——JWT 就是放在请求头里传的
- 客服服务独立开发、登录由其他服务负责，**完全可以用 JWT**，而且这就是 JWT 的典型应用场景（单点登录）

---

## 一、Token 流转全链路

```
登录成功 → 后端签发 JWT → 前端存 localStorage
                              ↓
                   前端请求时从 localStorage 取
                              ↓
              放在 Authorization: Bearer xxx 请求头里
                              ↓
              后端 AuthGuard 解析 token → 拿到 userId
                              ↓
              挂到 req.user，业务层直接用
```

### 前端侧（本项目）

`client/src/utils/request.ts`
- `getToken()` 从 `localStorage` 的 `ecom_token` key 取值
- `buildHeaders()` 自动加到 `Authorization: Bearer {token}`
- 401 时清除 token，派发 `auth:unauthorized` 事件

### 后端侧（本项目）

`server/src/common/auth/auth.guard.ts`
- 从 `request.headers['authorization']` 取 token
- `jwt.verify(token, secret)` 验签 + 解析
- 解析出的用户信息挂到 `request.user`
- 业务层从 `req.user.userId` 直接取

## 二、JWT 是什么？和"请求头传 token"的关系

| 概念 | 是什么 |
|---|---|
| **请求头带 token** | 传输方式——token 放在哪个位置传（header / body / query） |
| **JWT** | token 的**格式**——token 本身长什么样、怎么生成、怎么验证 |

> 不是二选一，而是"用什么格式的 token + 从哪里传"的组合。
> JWT 就是一种 token 格式，就是从请求头里传的。

### 为什么不能直接传 userId？

如果前端把 `X-User-Id: U-123` 直接放 header 里，后端直接读——**太不安全了**，用户可以随便改 header 伪造别人的身份。

**token 的核心作用是防伪**：有签名，后端用密钥验证，前端伪造不了。

## 三、常见 Token 方案对比

| 方案 | 原理 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|---|
| **JWT（无状态）** | 密钥签名，服务端直接验签 | 不用查库，快；水平扩展方便 | 签发后无法主动吊销 | 电商、互联网、微服务 |
| **随机串 + Redis** | 随机字符串存 Redis，每次查库 | 可随时吊销，更安全 | 每次请求多一次 IO | 金融、高安全要求 |
| **Session + Cookie** | 服务端存 Session，Cookie 带 SessionId | 传统方案，成熟 | 有状态，扩展麻烦 | 老项目、单体应用 |

## 四、独立服务 + 统一登录的场景（重点）

### 典型架构

```
┌─────────────┐     登录      ┌─────────────┐
│   前端项目   │ ────────────→ │  用户中心   │
│（独立团队）  │ ←──────────── │ （认证服务） │
└─────────────┘     JWT        └─────────────┘
       │
       │ 带 JWT 调用
       ▼
┌─────────────┐
│  客服服务    │  ← 本项目
│（独立开发）  │
└─────────────┘
```

### 客服服务要做的事

**只验证，不签发**：

1. 跟用户中心约定 JWT 密钥（对称加密 HS256 共用一个密钥）
2. 客服服务的 AuthGuard 用同一个密钥验签
3. 解析出 userId 注入业务上下文
4. 登录、注册、token 刷新全部交给用户中心

### JWT 里放什么（由用户中心决定）

```json
{
  "userId":   "U-123456",   // 必须有
  "username": "张三",        // 昵称
  "role":     "user",        // 角色
  "exp":      1718985600     // 过期时间
}
```

需要什么字段就跟用户中心协商加进去。

### 密钥方案选择

| 方案 | 说明 | 适用 |
|---|---|---|
| **HS256（对称）** | 所有服务共用一个密钥 | 内部服务，信任度高 |
| **RS256（非对称）** | 认证服务用私钥签发，其他服务用公钥验证 | 对外服务、安全性要求高 |

内部微服务一般 HS256 就够了，简单高效。

## 六、面试回答模板

> "我们这个客服系统是**独立开发的微服务**，登录认证由用户中心统一负责。
>
> 技术上用 **JWT 对称加密**，跟用户中心共享密钥：
> - 用户中心负责登录、签发 token
> - 我们客服服务只做 token 验签，解析出 userId 注入业务上下文
> - 这样既实现了单点登录，又不需要各服务重复做认证逻辑
>
> 之所以选 JWT，是因为它**无状态**，服务之间不需要共享会话存储，各服务独立验签就行，水平扩展也方便。
>
> 具体实现上，我在前端封装了统一的 request 工具，自动把 token 放到 Authorization header 里；
> 后端用 NestJS Guard 做了统一的认证中间件，解析出的用户信息挂到 request 上，
> Controller 和 Service 层直接用就行，不用每个接口都手动传 userId。"
