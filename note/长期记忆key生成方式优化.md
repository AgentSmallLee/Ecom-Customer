# 长期记忆 key 生成方式优化分析

## 当前方案

```ts
const memoryKey = (text: string) => `m_${text.slice(0, 60)}`;
```

用记忆文本前 60 个字符 + `m_` 前缀作为确定性 key。

## 方案优点

1. **幂等**：相同内容生成相同 key，重复写入即 upsert，不会重复插入
2. **简单高效**：O(1) 字符串截取，不依赖外部服务
3. **可观测**：key 本身就是内容前缀，排查问题时看 key 就知道大概是哪条记忆

## 已知局限

1. **语义重复**：语义相近但表述不同的记忆会被当成两条
   - 例："用户喜欢蓝色" 和 "用户偏爱蓝色" 是两条不同的 key
2. **截断风险**：60 字符以内相同但后面不同的记忆会互相覆盖（概率低，记忆一般是短句）
3. **无分类层级**：所有记忆平铺，条数多了后检索和管理不方便

## 是否需要优化？

**当前阶段不需要优化。**

理由：
- `MAX_MEMORIES = 10`，最多才 10 条，语义重复撑死两三条，对 LLM 理解影响微乎其微
- 优化成本（向量去重 / LLM 去重）远大于收益
- 优先保证功能稳定和可靠性，细节优化排在后面

## 优化方案对比（未来需要时）

| 方案 | 做法 | 效果 | 成本 |
|------|------|------|:----:|
| **向量相似度去重** | 每条记忆做 embedding，新记忆和已有记忆算余弦相似度，超阈值合并/替换 | 好 | 高（要引入向量检索流程） |
| **LLM 生成时去重** | 在 memoryWriter 的 prompt 里更强地要求合并语义相同的记忆 | 中等 | 低（改 prompt 就行） |
| **关键词归一化** | 同义词替换、词形归一化后再算 key | 一般 | 低（但规则难写全） |
| **记忆分类分层** | 按"偏好/历史订单/个人信息"等分类存储，同类内去重 | 好 | 中（要改存储结构和写入逻辑） |
| **重要性评分 + 淘汰** | 给每条记忆加重要性分，超上限时淘汰低分的 | 好 | 中（要加评分逻辑和淘汰策略） |

## 面试回答框架

> 三段式：当前方案是什么 → 有什么局限 → 未来怎么优化 + 为什么现在不做

这样既体现你对现状有清楚的认识，又说明你有技术判断力，知道什么时候该做什么事，不会为了优化而优化。

## 关联问题

- 为什么长期记忆最多 10 条？—— 电商客服场景，值得记住的用户偏好不多，10 条足够覆盖主要维度（尺码、颜色偏好、品牌偏好、称呼等），太多反而会干扰 LLM
- 如果要存更多记忆怎么办？—— 加向量检索，召回时按相似度取 Top N，而不是全量塞 prompt
