# 短期记忆相关问答笔记

> 梳理 chat / agent 页面短期记忆（checkpointer + threadId）的几个关键问题，都是开发过程中实际遇到或值得思考的点。

---

## 1. 刷新浏览器后，短期记忆还在吗？如何实现的？

**还在。** 靠两层持久化配合实现：

### 第一层：服务端持久化（根本保证）
短期记忆存在 PostgreSQL 的 `checkpoints` + `checkpoint_blobs` 表里，用 `PostgresSaver` 作为 checkpointer。

每次对话跑完一个节点，LangGraph 自动把完整的 State（包括 messages）序列化写进数据库。key 是 `thread_id`，只要 thread_id 不变，下次进来就能恢复完整状态。

### 第二层：前端记住 threadId（把用户和会话关联起来）
光服务端存了没用，用户刷新后浏览器不知道自己属于哪个 thread。所以前端把 `threadId` 存在 `localStorage` 里：

```ts
// 收到服务端返回的 threadId 时存下来
if (parsed.threadId) {
  threadId.value = parsed.threadId;
  localStorage.setItem(STORAGE_KEY, parsed.threadId);
}

// 页面加载时读出来，再去服务端拉历史
onMounted(async () => {
  const saved = localStorage.getItem(STORAGE_KEY);
  if (saved) {
    threadId.value = saved;
    await loadHistory();  // GET /api/chat/history?threadId=xxx
  }
});
```

### 完整流程
```
刷新页面
  ↓
onMounted 触发
  ↓
localStorage 读 threadId → 没有？全新会话，等用户发第一条消息
  ↓ 有？
GET /api/chat/history?threadId=xxx
  ↓
服务端 graph.getState() 从 checkpoint 恢复 messages
  ↓
前端用返回的 messages 渲染，UI 恢复如初
```

### 什么时候会丢？
- 用户点了"清空对话" → 前端清除 localStorage 的 threadId，服务端数据其实还在（只是前端找不到了）
- 用户清了浏览器 localStorage → 同上
- 数据库被删了 → 真没了

> 一句话：服务端的数据是持久的，前端只是拿了一把"钥匙"（threadId）。钥匙丢了就开不了门，但门里的东西还在。

## 2. 刷新后 AI 最后一条回复重复出现 — 为什么？怎么修？

### 现象
chat 页面刷新浏览器后，从服务端拉历史消息，发现最后一条 AI 回复总是重复出现两次。

### 根因
`chat.service.ts` 的 `stream` 方法里，流式生成结束后用 `graph.invoke()` 把消息写回 checkpoint：

```ts
// ❌ 错误写法
await this.graph.invoke(
  { messages: [new HumanMessage(message), new AIMessage(fullOutput)] },
  config,
);
```

`graph.invoke()` 不是简单的"追加消息"，而是**从头执行图**：
1. 把传入的 messages 追加到 state（Human + AI 都加进去了）
2. 执行 `chat` 节点，又调一次 LLM 生成回答
3. 把新生成的 AIMessage 也追加进去

结果就是 checkpoint 里多了一条 chat 节点生成的 AI 消息，刷新后读出来就看到重复了。

### 为什么 agent 页面没事？
agent 的 `invoke` 只传 `HumanMessage`，AI 消息是图节点正常产生的，只有一条。chat 的 stream 为了复用 chain.stream（拿 token 级流），先拿了答案再手动塞回去，用错了 API。

### 修复
用 `graph.updateState()` 替代 `graph.invoke()` — 前者只改状态、不执行节点：

```ts
// ✅ 正确写法
await this.graph.updateState(
  config,
  { messages: [new HumanMessage(message), new AIMessage(fullOutput)] },
);
```

### 教训
LangGraph 里 `invoke` / `stream` 是"执行图"，`updateState` 才是"改状态"。想用 checkpointer 当"消息存储"手动往里塞数据时，千万别用 invoke —— 它会带着整个图跑一遍。

## 3. 数据库的 metadata 字段里没有用户消息，正常吗？

**正常，这是 LangGraph PostgresSaver 的设计。**

### 三张表的分工

| 表 | 存什么 |
|---|---|
| `checkpoints` | checkpoint 元数据（版本号、channel_versions 等）+ `metadata` JSONB |
| `checkpoint_blobs` | **真正的状态数据**（messages 等 channel 值），存在 `blob BYTEA` 里 |
| `checkpoint_writes` | 中间写入状态 |

### metadata 存的是什么？
checkpoint 的**元信息**：`source`、`step`、`writes`、`parents` 等，用来过滤/查询 checkpoint，不是存业务状态的。

### 用户消息存在哪里？
在 `checkpoint_blobs` 表里，`channel = 'messages'` 的那行的 `blob` 字段。因为消息可能很大，LangGraph 把大的 channel 值序列化成二进制 blob 单独存，checkpoints 表只存轻量的元信息。

### 验证 SQL
```sql
-- 看 messages channel 的 blob
SELECT channel, version, type, length(blob) as blob_size
FROM checkpoint_blobs
WHERE thread_id = 'chat:xxx' AND channel = 'messages';
```

## 4. chat 页面就一个 chat 节点，有必要用 graph 吗？

**从当前功能看确实没必要，但从项目整体看有它的道理。**

### 为什么说"没必要"
就一个节点，完全可以用一个 chain + 自己操作 checkpointer 搞定，不需要套一层 StateGraph。代码量更少，概念更简单，也不会踩 invoke 导致重复消息的坑。

### 为什么还是用了

1. **架构一致性**：agent 模块、customer-graph 模块都用 LangGraph + checkpointer，chat 也用同一套模式。三个模块的记忆管理代码几乎一模一样（`withNamespace`、`graph.getState()`、`graph.updateState()` 裁剪）。新人看懂一个，另外两个也能看懂。

2. **统一用 MessagesAnnotation 的消息管理**：自带消息追加语义，不用自己写"读→追加→写回"的样板代码。裁剪也是用 `RemoveMessage` 统一模式。

3. **预留扩展位**：chat 现在是单节点，但未来可能加敏感词检测、摘要压缩、意图路由等节点。用 graph 的话加节点就是几行代码的事；不用 graph 就得重构。

### 结论
这是一个"**架构统一 > 局部最简**"的选择。单看 chat 模块是过度设计，但放在整个项目里（三个模块共享记忆层、共享 checkpointer、共享调试经验），这点"多余"的成本是值得的。

## 5. useChat 里的 messages 数组有用吗？

**有用，但它是"前端渲染用的副本"，不是"唯一真相源"。**

### 作用
1. **渲染当前对话**：Vue 响应式数据驱动 UI，v-for 渲染聊天记录
2. **承载流式输出过程**：流式生成时完整回复还没出来，需要响应式状态驱动 UI 更新
3. **优化体验**：用户点发送后立刻 push 一条用户消息，不用等服务端响应

### 但它不是真相源
短期记忆的真相源在**服务端 checkpoint** 里。前端 `messages` 只是一份缓存/副本：
- 刷新页面 → 从服务端拉历史，重新填充
- 发送消息 → 先本地 push 占位，等 AI 回复后再 push 完整消息

### 潜在不一致风险
- **发送失败**：用户消息已经 push 进去了，但请求失败 → 需要回滚（当前代码没处理，是个小 bug）
- **多标签页**：同一个 threadId 在两个标签页聊天 → 两边 messages 不同步

### 如果不用行不行？
理论上可以每次发完都重新拉历史，但体验差（自己发的消息要等请求回来才显示）、流式输出没法做、浪费流量。

所以 `messages` 数组是**必要的前端状态**，它和服务端 checkpoint 是"缓存 + 真相源"的关系。

## 6. 首次对话时，threadId 是前端生成还是后端生成？

**后端生成的。**

### 完整流程
1. 前端初始 `threadId = ''`，localStorage 里也没有
2. 发第一条消息时，threadId 为空就不传（`threadId: threadId.value || undefined`）
3. 后端收到后：`const tid = threadId || randomUUID()` — 没传就生成一个新 UUID
4. 后端 SSE 第一帧就发 threadId：`sendData({ threadId: tid })`
5. 前端收到后保存到 ref + localStorage

### 为什么让后端生成？
| | 前端生成 | 后端生成 |
|---|---|---|
| 优点 | 不用等第一帧就知道 threadId | 统一入口，保证全局唯一，前端逻辑简单 |
| 缺点 | 要引入 uuid 库，考虑碰撞（极低） | 前端要等 SSE 第一帧才能拿到 |

当前项目选后端生成的原因：
1. 前端不用额外引入 uuid 依赖，少一个包
2. 逻辑更简单 — 前端只管"有就传，没有就等服务端给"
3. agent/chat/graph 三个模块统一模式
