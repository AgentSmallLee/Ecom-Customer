# 数据库创建时机

企业项目中，"数据库"包含三层：**数据库实例**、**数据库（database / schema）**、**数据表**。它们的创建时机和负责方各不相同。

## 四层创建时机总览

| 层级 | 创建者 | 时机 | 典型工具 |
|------|--------|------|---------|
| 数据库实例（PostgreSQL 服务） | 运维 / SRE | 项目立项初期，基础设施阶段 | Terraform / 云控制台 / 阿里云 RDS |
| 数据库（database，如 ecom_ai） | 运维 / DBA | 应用首次部署前 | SQL / 云控制台 / Terraform |
| 扩展（如 pgvector） | 运维 / DBA | 应用首次部署前 | CREATE EXTENSION |
| 表结构（表、索引、字段） | 开发团队 | 每次部署时自动执行 | Prisma Migrate / TypeORM / Flyway / Liquibase |

## 四种常见模式

### 1. IaC 基础设施即代码（中大型企业标准做法）

数据库实例和库由运维团队通过 Terraform / Pulumi 定义和创建。

- **时机**：项目立项初期，在应用部署之前就建好
- **负责方**：运维 / SRE / DBA
- **应用代码**：只负责连接数据库和管理表结构，不负责创建数据库
- **原因**：
  - 安全隔离：应用运行账号没有 CREATE DATABASE 权限
  - 资源管控：数据库规格、备份、监控统一由基础设施管理
  - 多环境一致：dev / staging / prod 用同一套配置文件创建

### 2. 应用启动时执行 Schema 迁移（最常见的表管理方式）

表结构变更通过迁移工具管理，部署时自动执行。

- **工具**：Prisma Migrate、TypeORM Migrations、Flyway、Liquibase
- **时机**：每次 CI/CD 部署流程中，应用启动前执行
- **特点**：
  - 每个迁移是一个版本化的 SQL 脚本
  - 有回滚机制（部分工具支持）
  - 多实例部署时通过锁表防止并发执行
- **不做的事**：不创建数据库实例，不创建 database，只管理表/索引/字段

### 3. 独立初始化脚本（开发/测试环境常用）

像本项目的 `init-db.ts`，手动执行一次。

- **时机**：本地开发环境首次搭建时，或测试环境重置时
- **负责方**：开发同学手动执行
- **适用场景**：
  - 小项目快速原型
  - 本地开发环境一键初始化
  - 还没引入迁移工具的早期阶段
- **注意**：
  - 脚本必须幂等（CREATE ... IF NOT EXISTS）
  - 创建数据库时要先连到默认库（postgres / template1），不能直连目标库
  - 生产环境不要用这种方式

### 4. 应用启动时自动初始化（小项目/原型，不推荐生产用）

在 `main.ts` 启动时调用初始化逻辑：

```ts
await initDatabase();
await app.listen(PORT);
```

- **优点**：部署简单，不用手动执行脚本
- **缺点**：
  - 多实例部署有并发问题
  - 应用账号需要高权限，有安全风险
  - 数据库挂了应用也起不来，排障困难
- **适用**：单实例的小项目、demo、原型

## 本项目的推荐做法

| 环境 | 数据库（实例+库） | 表结构 |
|------|-------------------|--------|
| **本地开发** | `pnpm run init-db` 手动执行一次 | init-db 脚本里建表（IF NOT EXISTS） |
| **测试环境** | 运维提前建好，或 CI 里执行 init-db | init-db 脚本 + 后续逐步引入迁移工具 |
| **生产环境** | 运维/DBA 提前创建，应用账号只有读写权限 | 引入 Prisma / TypeORM 迁移工具 |

**长期方向**：引入迁移工具管理 schema 变更，`init-db` 只保留为本地开发的便利脚本。
