# 审计日志写入失败排查记录

> **问题一句话总结**：给 RAG 流程的审计日志补充 `userId` / `threadId` 后，审计日志反而完全写不进数据库了。
>
> **根因一句话总结**：`schema.prisma` 里新增的 `userId` / `threadId` 字段**从未生成过对应迁移**，真实数据库表缺少这两列；改动前传的是 `undefined`（Prisma 会自动省略该列，所以能写入），改动后传了真实值（Prisma 把列拼进 INSERT），于是 SQL 报错 `column does not exist`，而异常又被 `try/catch` 静默吞掉了。

---

## 一、问题现象

| 项 | 表现 |
|---|---|
| 数据库 | `llm_audit_logs` 表没有任何新增数据 |
| 接口 | 正常返回，业务功能不受影响 |
| 控制台 | 没有异常堆栈，只有 `AuditLogService` 内部的 error 日志 |
| 触发时机 | 在 RAG 流程中传入真实 `userId` / `threadId` 之后 |

关键特征是：**静默失败**——不崩溃、不报错，只是数据没了。这类问题比直接抛错更难排查。

---

## 二、涉及的数据流

审计日志的写入链路贯穿 4 层：

```
HTTP 请求
  │
  ├─ Controller          取 req.user.userId，生成/透传 threadId
  │                      server/src/rag/rag.controller.ts
  │
  ├─ Service             把 source / traceId / userId / threadId 放进 call options
  │                      server/src/rag/rag.service.ts
  │
  ├─ FailoverChatModel   extractMetadata() 从 call options 提取这 4 个字段
  │                      每次 LLM 调用结束后调用 writeAudit()
  │                      server/src/llm/failover-chat-model.ts
  │
  └─ AuditLogService     prisma.llmAuditLog.create({ data: payload })
                         server/src/llm/audit-log.service.ts
                              │
                              └─→ llm_audit_logs 表 ← ★ 问题出在这里
```

本次改动的范围只涉及前两层（Controller / Service），后两层早在之前的迭代中就已经支持 `userId` / `threadId` 了，所以当时判断「不用改」是合理的——**问题不在代码，在数据库**。

---

## 三、排查过程

### 第 1 步：确认代码链路没问题

先跑类型检查，确认新增的 `threadId` 参数在各层签名上都能对上：

```bash
npx tsc --noEmit
# 无输出 → 通过
```

代码链路是通的，说明问题不在调用关系上。

### 第 2 步：看 schema.prisma —— 字段定义存在

```prisma
model LlmAuditLog {
  id            String    @id @default(cuid())
  traceId       String?   // 请求链路 ID
  userId        String?   // 用户 ID，来自 JWT
  threadId      String?   // 会话 ID
  ...
  @@index([userId, createdAt])
  @@index([threadId])
  @@map("llm_audit_logs")
}
```

字段是**可空的 String**，类型上没有任何问题。

### 第 3 步：看迁移文件 —— 发现疑点 ⚠️

`prisma/migrations/` 下只有一个迁移 `0000_init`，它的建表语句是：

```sql
CREATE TABLE "llm_audit_logs" (
    "id" TEXT NOT NULL,
    "traceId" TEXT,
    "source" TEXT NOT NULL,
    ...
    "createdAt" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT "llm_audit_logs_pkey" PRIMARY KEY ("id")
);
```

**`userId` 和 `threadId` 根本没出现过**。连索引也没有。
→ 说明 schema.prisma 添加这两个字段时，**没有同步生成迁移**。

### 第 4 步：看真实数据库表 —— 确认疑点 ✅

```bash
psql "postgresql://mac@localhost:5432/ecom_ai" -c "\d llm_audit_logs"
```

输出中只有 `id / traceId / source / model / provider / isFailover / promptPreview / inputTokens / outputTokens / totalTokens / status / latencyMs / errorMessage / createdAt` 这几列，**确实没有 `userId` 和 `threadId`**。

> 📌 **字段名说明**：`inputTokens` 在本次排查时还叫 `promptTokens`。后来为统一命名体系（`inputTokens` / `outputTokens` / `totalTokens`）做过一次重命名，由 [0002_rename_prompt_tokens_to_input_tokens](./prisma/migrations/0002_rename_prompt_tokens_to_input_tokens/migration.sql) 迁移完成。
>
> ⚠️ 该迁移用的是 `RENAME COLUMN` 而**不是** `DROP + ADD`——因为 Prisma 无法识别"改名"，`migrate diff` 会自动生成 `DROP COLUMN "promptTokens" / ADD COLUMN "inputTokens"`，那样会把该列已有数据全部清空（本次涉及 3 行、合计 88 tokens，已确认完整保留）。

### 第 5 步：看迁移历史记录

```bash
psql "postgresql://mac@localhost:5432/ecom_ai" \
  -c "SELECT migration_name, finished_at FROM _prisma_migrations ORDER BY finished_at;"
```

```
 migration_name |          finished_at
----------------+-------------------------------
 0000_init      | 2026-09-11 17:37:34.986858+08
```

只有 `0000_init` 一条，印证了「字段加进 schema 后从没建过迁移」这个判断。

### 第 6 步：确定性验证 —— 手动复现错误

不再靠推理，直接模拟 Prisma 会发出的 SQL：

```bash
psql "postgresql://mac@localhost:5432/ecom_ai" \
  -c "INSERT INTO llm_audit_logs (id, source, model, provider, status, \"latencyMs\", \"userId\", \"threadId\")
      VALUES ('test-id','rag-chain','m','p','success',1,'u1','t1');"
```

```
ERROR:  column "userId" of relation "llm_audit_logs" does not exist
第1行...id, source, model, provider, status, "latencyMs", "userId", ...
                                                          ^
```

**这就是根因的直接证据**。

### 第 7 步：确认生成的 Prisma Client 是新的

```bash
# 生成产物里已经包含这两个字段
src/generated/prisma/models/LlmAuditLog.ts:46:  userId: string | null
src/generated/prisma/models/LlmAuditLog.ts:47:  threadId: string | null
```

所以是一边新（Client 有字段）、一边旧（数据库没列）——**编译期完全发现不了，只有运行时写库才炸**。

## 四、根因分析

### 4.1 直接原因：Schema 漂移（Schema Drift）

即 `schema.prisma` 声明的结构与真实数据库结构**不一致**：

| 位置 | userId / threadId |
|---|---|
| `schema.prisma`（声明） | ✅ 有 |
| 迁移文件（历史） | ❌ 没有 |
| 生成的 Prisma Client | ✅ 有 |
| **真实数据库表** | ❌ **没有** |

### 4.2 为什么之前"看起来是好的"：Prisma 对 `undefined` 的处理

这是问题的关键，也是最容易踩坑的地方。

**Prisma 的行为：字段值为 `undefined` 时，会从 INSERT 语句中省略该列；值为 `null` 或具体值时，才会带上该列。**

| 阶段 | 代码传给 Prisma 的值 | 生成的 SQL（简化） | 结果 |
|---|---|---|---|
| **改动前** | `userId: undefined`（未登录或未传）<br>`threadId: undefined` | `INSERT INTO llm_audit_logs (id, source, model, ..., traceId) VALUES (...)` | ✅ 不涉及缺失的列，写入成功 |
| **改动后** | `userId: 'user-123'`<br>`threadId: 'xxxx-uuid'` | `INSERT INTO llm_audit_logs (id, source, model, ..., userId, threadId) VALUES (...)` | ❌ `column "userId" does not exist` |

所以并不是「加字段把功能改坏了」，而是**改动只是把一个一直存在的隐患暴露了出来**。

> 补充说明：`chat` / `agent` 模块如果传了真实 `userId` / `threadId`，同样会写入失败。这是同一处漂移导致的共性问题，只是这次 RAG 改动先撞上了。

### 4.3 为什么没有任何报错：异常被静默吞掉

`AuditLogService.write()` 为了保护主流程，把所有异常都 catch 掉了：

```ts
// server/src/llm/audit-log.service.ts
async write(payload: AuditLogPayload): Promise<void> {
  try {
    await this.prisma.llmAuditLog.create({ data: payload })
  } catch (e) {
    // 日志写失败不能影响主流程，只打本地 log
    this.logger.error('审计日志写入失败', e)
  }
}
```

这个设计本身是**合理的**（审计日志不该拖垮业务），但代价是：
- 业务接口一切正常，没有任何异常冒泡到用户
- 错误只落在 Nest 的 Logger 里（`[AuditLogService] 审计日志写入失败`）
- 如果没盯着服务端日志，就会完全无感

### 4.4 为什么 `prisma migrate status` 显示一切正常

```
$ npx prisma migrate status
1 migration found in prisma/migrations
Database schema is up to date!      ← 具有迷惑性
```

因为 `migrate status` 只做一件事：**检查「迁移历史」里记录的迁移是否都已应用到数据库**。

它比对的是：`_prisma_migrations` 表的记录 ↔ `prisma/migrations/` 目录里的文件。
它**不会**去比对 `schema.prisma` ↔ 真实数据库结构。

所以即使 0000_init 里漏了字段，只要它被标记为已应用，status 就永远是 "up to date"。
→ **结论：不能用 `migrate status` 来验证 schema 与数据库是否一致。**

### 4.5 为什么 TypeScript 类型检查通过

Prisma Client 是从 `schema.prisma` **生成**的，它「相信」数据库里有 `userId` / `threadId`，所以生成的类型里带上这两个字段，编译自然通过。

类型系统在这里帮不上忙——**它校验的是代码与 Client 的一致性，而不是 Client 与数据库的一致性**。

## 五、解决方案

### 5.1 生成差异 SQL（确认要补什么）

Prisma 7 的 `migrate diff` 可以直接把「当前数据库 → schema.prisma」的差异输出成 SQL：

```bash
npx prisma migrate diff \
  --from-config-datasource \
  --to-schema prisma/schema.prisma \
  --script
```

输出：

```sql
-- AlterTable
ALTER TABLE "llm_audit_logs" ADD COLUMN     "threadId" TEXT,
ADD COLUMN     "userId" TEXT;

-- ✂️ 省略：以下 DropTable 是因为项目里有非 Prisma 管理的表，见下方说明
-- DropTable
DROP TABLE "checkpoint_blobs";
-- DropTable
DROP TABLE "checkpoints";
-- DropTable
DROP TABLE "knowledge_embeddings";
-- DropTable
DROP TABLE "store";
-- ...

-- CreateIndex
CREATE INDEX "llm_audit_logs_userId_createdAt_idx" ON "llm_audit_logs"("userId", "createdAt");

-- CreateIndex
CREATE INDEX "llm_audit_logs_threadId_idx" ON "llm_audit_logs"("threadId");
```

> ⚠️ **重要提醒**：`migrate diff` 的输出里会包含一堆 `DROP TABLE`，那是因为 `checkpoints`、`knowledge_embeddings`、`store` 等表是由 LangGraph 和 `init-db.ts` 在 Prisma 之外创建的，schema.prisma 里没有它们。
> **这些 DROP 语句绝对不能执行**，只能取 `llm_audit_logs` 相关的那几行。

> 📌 参数差异说明：Prisma 7 移除了旧参数。`--from-schema-datasource` / `--to-schema-datamodel` 已废弃，需改用 `--from-config-datasource` / `--to-schema`。

### 5.2 新增迁移文件

创建 `prisma/migrations/0001_add_user_thread_id/migration.sql`，只保留 `llm_audit_logs` 的变更：

```sql
-- AlterTable
ALTER TABLE "llm_audit_logs" ADD COLUMN     "threadId" TEXT,
ADD COLUMN     "userId" TEXT;

-- CreateIndex
CREATE INDEX "llm_audit_logs_userId_createdAt_idx" ON "llm_audit_logs"("userId", "createdAt");

-- CreateIndex
CREATE INDEX "llm_audit_logs_threadId_idx" ON "llm_audit_logs"("threadId");
```

目录命名沿用项目的序号风格（`0000_init` → `0001_xxx`），保证排序正确。

### 5.3 应用迁移：用 `migrate deploy`，不要用 `migrate dev`

```bash
npx prisma migrate deploy
```

```
Applying migration `0001_add_user_thread_id`
All migrations have been successfully applied.
```

**为什么不走 `migrate dev`？**

因为数据库里存在大量**非 Prisma 管理**的表（`knowledge_embeddings`、`checkpoints*`、`store*`），`migrate dev` 会做漂移检测，很可能提示 **"Drift detected"** 并要求**重置数据库**——那会直接干掉向量库里的知识数据。

各命令对比：

| 命令 | 是否检测漂移 | 是否会重置数据库 | 适用场景 |
|---|---|---|---|
| `migrate dev` | ✅ 会 | ⚠️ 可能 | 开发环境，Prisma 独占数据库 |
| `migrate deploy` | ❌ 不会 | ❌ 不会 | **多系统共用库 / 生产环境（本项目）** |
| `migrate resolve --applied` | ❌ 不会 | ❌ 不会 | 只标记迁移状态，不执行 SQL |
| `db push` | ✅ 会 | ⚠️ 可能 | 原型阶段，直接同步结构、不留迁移记录 |

这也和 [PRISMA_SETUP.md](./PRISMA_SETUP.md) 中「方案 A：Prisma 只管理自己的表」的思路一致。

## 七、经验总结与预防措施

### 7.1 改了 `schema.prisma` 就必须配迁移

**这是本次问题的根本教训。** 即使是「只加一个可空字段」这种看起来无风险的操作，也必须生成迁移：

```bash
# 推荐流程
npx prisma migrate dev --name add_xxx --create-only   # 只生成 SQL，先 review
npx prisma migrate deploy                             # 再应用到目标库
```

> 本项目因多系统共库，建议用 `--create-only` 生成后人工检查 SQL，避免误删非 Prisma 表。

### 7.2 `migrate status` ≠ 结构一致

`migrate status` 只比对迁移历史，**不检测 drift**。
要验证 schema 与真实库是否一致，用：

```bash
npx prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script
```

**输出为空（忽略 DropTable 部分）才算真正一致。**

### 7.3 排查"静默失败"的一般思路

遇到「代码没报错，但数据没落库」，按这个顺序查：

1. **先找 try/catch** —— 错误是不是被吞了？翻服务端日志找 `error` 级别的记录
2. **确认目标表/列真实存在** —— 用 `psql \d <table>` 直接看，不要相信 ORM 的声明
3. **比对 ORM 声明与真实结构** —— 极可能是 schema drift
4. **手动复现最小 SQL** —— 绕开所有框架，直接用 `psql` 跑一遍 INSERT，看真实报错
5. **确认生成产物是否最新** —— ORM 的 Client / Model 是否已重新生成

### 7.4 可选改进：让审计失败更醒目

当前 `catch` 里只打了一条 error log，字段信息不足，定位时较难。可以考虑补上上下文（**属于可选优化，本次未改**）：

```ts
} catch (e) {
  this.logger.error(
    `审计日志写入失败 source=${payload.source} traceId=${payload.traceId} ` +
    `userId=${payload.userId} threadId=${payload.threadId}: ${e instanceof Error ? e.message : e}`
  )
}
```

### 7.5 重建数据库的完整流程（重要）

`init-db.ts` **只负责**：
- 建 `knowledge_embeddings` 表 + pgvector / pg_trgm 扩展 + 索引
- 初始化 LangGraph 的 `checkpoints*` / `store*` 表

它**不创建 `llm_audit_logs`**！该表由 Prisma 迁移负责。

所以将来重建数据库时，两步都要做，缺一不可：

```bash
# 1. 业务表 + 向量表 + 记忆表
pnpm run init-db

# 2. Prisma 管理的表（llm_audit_logs）
npx prisma migrate deploy

# 3. 灌入知识库数据
pnpm run ingest
```

漏掉第 2 步的话，审计日志又会写不进去，且症状和本次一模一样。
